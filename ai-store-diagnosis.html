CASE STUDY

AI 门店资产质量诊断

从人工排查到标准化诊断链路

面向门店复杂异常，设计一套以门店 ID 为入口的诊断工作台，把取数进度、归因证据、风险结论和修正动作集中在同一页面。

分钟级初步归因 责任争议下降 60%+ 归因复核通过试点验证
我的角色
AI 产品经理 / Agent 方案负责人
产品形态
门店 ID 驱动的异常诊断工作台
负责范围
问题抽象、归因体系、Agent 工作流、模型边界、核心场景验证
交付产出
标准化诊断链路、字段级 / Case 级归因结果、责任路由方案

Problem

业务痛点与破局点

本地生活交易需要向 C 端用户展示门店详情页，并支撑搜索、导航、到店核销等关键链路。门店数据不是后台资料，而是直接影响用户能不能找到店、到不了店、核不了券的交易基础设施。

痛点一

排查链路长，处理节奏慢

复杂异常 Case 往往需要跨多张表查看当前值、推荐值、变更记录和流程信息。单个 Case 人工排查通常需要半小时级甚至更久。

痛点二

归因标准不统一

同一类异常可能被归到提报、审核、写入或维护等不同环节。缺少统一的字段级、Case 级归因口径，后续责任流转和修复动作也会反复拉齐。

痛点三

人工经验难沉淀

人工投入足够时间可以查到问题所在，但过程依赖个人经验，难以稳定复用。真正需要沉淀的是错误怎么来的、哪个环节本该拦截、后续应该如何处理。

这个项目承接门店供给治理中沉淀的复杂异常样本和规则边界，将证据聚合、归因判断和处理建议标准化，让业务和运营可以更快完成判断与处置。

Impact

核心成果与交付价值

这个项目的交付价值，是把运营人员的复杂排查经验沉淀为 AI 可执行的诊断链路，让异常归因从人工查证变成系统化判断。

指标层级 业务基线 方案结果 价值说明
排查效率 人工单 Case 排查耗时较长 系统分钟级产出初步归因报告，排查时长缩短 80%+ 变更触发走分钟级诊断，巡检异常按批量节奏归因。
责任一致性 依赖运营经验判断，标准不一 责任归因争议下降 60%+ 以历史人工判断分歧和二次改判为基线，系统统一输出主因、次因、辅因和责任阶段，减少后续争议与返工。
结论质量 依赖人工复核，口径不稳定 核心归因结论通过人工复核验证 由业务专家抽检系统输出的主因、次因、辅因结论，判断是否足以支撑责任判断和后续处理。
能力沉淀 人工流程分散，难复用 沉淀 4 类核心异常场景的诊断口径 形成可复用的门店数据问题排查框架。

归因体系设计

将人工排查经验抽象为主因、次因、辅因三层体系，明确字段级和 Case 级结果如何输出。

AI 工作流设计

设计信息溯源、多源比对、归因判断、责任路由等核心能力，并拆分 Agent、规则引擎和解释展示职责。

核心场景验证

基于真实复杂异常场景验证诊断链路可行性，评估排查时长、责任归因一致性和结论可解释性。

Workflow

诊断链路与用户动线

运营人员输入门店 ID 后，左侧可查看取数、比对和归因进度，右侧获得风险等级、关键变更证据与处理建议；确认结论后，可直接发起修正。

覆盖诊断范围：门店基础信息 ｜ 资产关系错乱 ｜ 真实性校验 ｜ 唯一性定位失败

系统先承接巡检、人工确认、审核驳回和业务反馈等异常入口，再判断问题属于门店基础信息错误、资产关系错乱、真实性异常还是门店唯一性定位失败。

系统基于证据链判断主因、次因、辅因，并给出对应处理动作，后续可以继续跟进修复状态和处理结果。

Guardrails

架构设计与大模型行为边界

异常归因不能让模型直接猜原因。我的设计原则是：规则负责可验证判断，模型只处理规则覆盖不了的语义判断，每个结论都要有依据可查。

编排

主 Agent

负责理解用户输入、识别诊断意图、抽取必要参数，并决定进入哪条诊断链路。

确定性

规则与执行计划层

负责参数校验、信息查询计划、值比对、差异分类、事件分层、置信度计算等任务。

语义

LLM 辅助判断

当规则无法判断时，只基于已有证据处理品牌主干、地址差异、多字段变化等语义判断。

输出

解释与展示层

将结构化诊断结果翻译成业务人员能理解的归因说明，并组织字段级、Case 级报告。

这套架构的价值，是把“找证据”和“下结论”拆开：Agent 编排查询流程，规则和工具完成取数与确定性校验，LLM 只基于证据处理语义判断和业务解释。

Iteration

演进历程与落地反思

这次复盘最大的收获，是把诊断系统里哪些靠规则、哪些靠模型、哪些靠产品流程承接，拆得更清楚。

01

别让模型越过证据下结论

早期让模型直接判断名称、地址是否异常时，结论不够稳定。后来改为 Agent 先编排证据查询，规则和工具完成取数与确定性校验。

LLM 只基于证据处理品牌相似、地址差异等语义判断。这样保留理解能力，也避免模型直接拍结论。

02

归因不是找错，是还原链路

主因、次因、辅因不是给责任方贴标签，而是说明错误怎么发生。提报、审核、写入、维护，每个环节都可能出问题。

只有把链路讲清楚，后续才知道该谁处理、怎么处理、是否需要复核。

03

工具调用先定计划

模型不应该自由试工具。系统先生成执行计划，再按计划取门店特征、参考值和变更记录；失败时直接兜底。

理解、执行、解释、展示分开后，换页面或换输出格式时，不需要重写诊断逻辑。
